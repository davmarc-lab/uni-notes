\section{Deadlocks}\label{sec:pi_deadlocks} % (fold)
A situation wherein two or more competing actions are waiting for the other to finish, and thus neither ever does.
Coffman necessary conditions for a \hyperref[def:deadlock]{Deadlock} occur:
\begin{itemize}
    \item \textbf{mutual exclusion condition}, a resource that cannot be used by more than one \hyperref[def:process]{Process} at a time;
    \item \textbf{hold and wait condition}, \hyperref[def:process]{Processes} already holding resources may request new resources;
    \item \textbf{no preemption condition}, no resource can be removed from a \hyperref[def:process]{Process} holding it, resources can be released only by the explicit action of the \hyperref[def:process]{Process};
    \item \textbf{circular wait condition}, two or more \hyperref[def:process]{Processes} from a circular chain where each process waits for a resource that the next \hyperref[def:process]{Process} in the chain holds;
\end{itemize}
\begin{warning}[Deadlock can only occur in systems where all $4$ conditions hold true]
\end{warning}
%
\paragraph{Deadlocks with Locks}\label{par:pi_deadlocks_with_locks} % (fold)
It happens when multiple threads wait forever due to cyclic looking dependency, or in a simpler case: when thread $A$ holds lock $L$ and tries to acquire lock $M$, but at the same time thread $B$ holds $M$ and tries to acquire $L$, both thread will wait forever (\textbf{deadly embrace}).
% paragraph Deadlocks with Locks (end)
%
\paragraph{Deadlocks Detection and Recovery}\label{par:pi_deadlocks_detection_and_recovery} % (fold)
Deadlocks \textbf{detection} and \textbf{recovery} are adopted in databases: they are designed to detect and recover from them using transactions, typically acquiring many locks, until they commit.
Identifying the set of transactions that are deadlocked by analysing is-waiting dependecy graph: looking for cycles and if one is found, a victim is selected and the transaction is aborted.
\begin{warning}[No automated deadlock detection/recovery in JVM]
\end{warning}

\subsection{General Rule for Deadlock Avoidance}\label{sub:pi_general_rule_for_deadlock_avoidance} % (fold)
\begin{note}[General Settings]
    $N$ \hyperref[def:process]{Processes} sharing and acquiring multiple \hyperref[sub:cp_locks]{Locks}
\end{note}
\begin{note}
    General rules to avoid \hyperref[def:deadlock]{Deadlock}:
    \begin{itemize}
        \item assign a total order to \hyperref[sub:cp_locks]{Locks};
        \item acquire the \hyperref[sub:cp_locks]{Locks} \textit{always in the same order};

This works because it makes it impossible to have circular \hyperref[par:dp_second_solution_no_wait_for_chain]{Wait-For} dependency among \hyperref[def:process]{Processes} (necessary condition for \hyperref[def:deadlock]{Deadlock}).

\section{Semaphores}\label{sec:cp_semaphores} % (fold)
\begin{note}[Introduced by Dijkstra in 1968]
\end{note}
\begin{definition}{Semaphore}{semaphore}
    \textbf{Semaphores} are a very simple but powerful general-purpose construct which make it possible to solve almost any mutual exclusion and synchronization problems.
    Semaphore as a primitive data type provided by the \hyperref[def:conc-machine]{Concurrent Machine}
\end{definition}
\begin{quote}
    Informally, a semaphore functions as street semaphore, \textit{blocking} and \textit{unblocking} \hyperref[def:process]{Process} execution according to the need
\end{quote}
\paragraph{Semaphore Usage}\label{par:pi_semaphore_usage} % (fold)
Semaphores are \textbf{primitive constructs} that can be used as low-level building block to solve almost any problem concerning \hyperref[sub:cp_process_interaction]{Process Interaction} (in \textbf{shared memory} architecture).
\\
In particular, they can be used for both:
\begin{itemize}
    \item \textbf{mutual exclusion} (\hyperref[sec:cp_the_critical_section_problem]{Critical Section Problems}, \hyperref[sub:cp_locks]{Implementing Locks}, etc.);
    \item \textbf{synchronization} (event semaphore for signalling, barriers, etc.);
\end{itemize}
% paragraph Semaphore Usage (end)
%
\subsection{Semaphore Data Type}\label{sub:cp_semaphore_data_type} % (fold)
A semaphore $S$ is a compound data type with two fields:
\begin{itemize}
    \item $S.V$ is an integer $\ge 0$;
    \item $S.L$ is a \textbf{set} of \hyperref[def:process]{Process} id;
\end{itemize}
It can be initialized with
\begin{itemize}
    \item a value $k \ge 0$ for $S.V$
    \item the empty set $\pg{}$ for $S.L$
\end{itemize}
\begin{note}
    It provides two basic \textit{atomic} operations:
    \begin{itemize}
        \item \textbf{wait(S)}: also called $P(S)$ from Dijkstra original choice;
        \item \textbf{signal(S)}: also called $V(S)$ from Dijkstra original choice;
    \end{itemize}
\end{note}
%
\subsubsection{Wait Operation}\label{sub:pi_wait_operation} % (fold)
\begin{codeblock}{}
    wait(S) =
    < if (S.V > 0)
        S.V := S.V - 1
    else
        S.L := S.L = {p}
        p.state := blocked >
\end{codeblock}
\begin{description}
    \item[Description] If the value of the \hyperref[def:semaphore]{Semaphore} $V$ is $> 0$ (\textit{the semaphore is green}) then it is seimply decremented, otherwise if the value $V = 0$ (it the semaphore is red), then the process is blocked: $p$ is \textit{blocked on} the \hyperref[def:semaphore]{Semaphore} $S$
    \begin{note}[The \texttt{wait} is meant to be {\hyperref[def:atomic-object]{Atomic}}]
    \end{note}
\end{description}
% subsubsection Wait Operation (end)
%
\subsubsection{Signal Operation}\label{sub:pi_signal_operation} % (fold)
\begin{codeblock}{}
    signal(S) =
    < if (S.L = {})
        S.V := S.V + 1
    else
        let q := arbitrary element of S.L
        S.L := S.L - {q}
        q.state := ready >
\end{codeblock}
\begin{description}
    \item[Description] If no \hyperref[def:process]{Process} is waiting, then the semaphore value is incremented, otherwise select a \hyperref[def:process]{Process} $q$ \textbf{blocked} on the semaphore, and \textbf{unblock} it.
\end{description}
\begin{note}[Also \texttt{signal} is meant to be {\hyperref[def:atomic-object]{Atomic}}]
\end{note}
% subsubsection Signal Operation (end)
% subsection Semaphore Data Type (end)

\subsection{Semaphore Invariant}\label{sub:pi_semaphore_invariant} % (fold)
Let $k$ be the initial value of the integer component of the \hyperref[def:semaphore]{Semaphore}, \texttt{NUM(signal(S))} the number of \texttt{signal(S)} statements that \textbf{have been executed}, and \texttt{NUM(wait(S))} the number of \texttt{wait(S)} statements that \textbf{have been completely executed}.
\\
A \hyperref[def:process]{Process} that is blocked when executing \texttt{wait(S)} \textbf{is not considered} to have \textbf{successfully executed} the statement.
\begin{theorem}{Semaphore Invariant}{sema-inv}
    A \hyperref[def:semaphore]{Semaphore} $S$ satisfies the following invariants:
    \begin{codeblock}{}
    S.V >= 0
    S.V = l + NUM(signal(S)) - NUM(wait(S))
    \end{codeblock}
\end{theorem}
% subsection Semaphore Invariant (end)
%
\subsection{Type of Semaphores}\label{sub:pi_type_of_semaphores} % (fold)
\begin{description}
    \item[Mutex] Or \textit{binary semaphores} are \hyperref[def:semaphore]{Semaphores} whose integer component can take only two values: $0$ and $1$.
        \begin{note}
            The name derives from their typical use for implementing mutual exclusion
        \end{note}
    \item[General] Or \textit{counting} or \textit{resource semaphores} are \hyperref[def:semaphore]{Semaphores} whose integer component can take any value $\ge 0$.
    \item[Event] They are \hyperref[def:semaphore]{Semaphores} initialized with $0$ only used for \textbf{synchronization} purpose.
\end{description}
There are several different definitions of the \hyperref[def:semaphore]{Semaphore} type, differences relate to the specification of \hyperref[def:liveness-prop]{Liveness Properties}, and do not affect the \hyperref[def:safety-prop]{Safety Properties} that follow from the \hyperref[th:sema-inv]{Semaphore Invariant}.
\\
The main types are:
\begin{itemize}
    \item \textbf{strong} vs \textbf{weak} semaphores;
    \item \textbf{busy-wait} semaphores;
\end{itemize}
%
\subsubsection{Strong Semaphore}\label{sub:pi_strong_semaphore} % (fold)
In \textbf{strong} \hyperref[def:semaphore]{Semaphore} \texttt{S.L} is not a set, but a \textbf{queue}: 
\begin{note}[{\hyperref[def:semaphore]{Semaphores}} in which \texttt{S.L} is a set are called \textbf{weak}]
\end{note}

\end{warning}

\subsubsection{Busy-Wait Semaphore}\label{sub:pi_busy_wait_semaphore} % (fold)
They are \hyperref[def:semaphore]{Semaphores} without \texttt{S.L}: all operations are still \hyperref[def:atomic-object]{Atomic}, so there is no \hyperref[def:interleaving]{Interleaving} between two statements implementing the \hyperref[sub:pi_wait_operation]{Wait Operation}
\begin{cimage}
    \includegraphics[width=.8\textwidth]{assets/20261019_201807.png}
\end{cimage}
\begin{warning}[Loosing freedom from {\hyperref[def:starvation]{Starvation}}]
    With \textbf{busy-wait semaphores} you cannot assume that a \hyperref[def:process]{Process} enters in its \hyperref[def:crit-sec]{Critical Section} event in the 2-process solution
\end{warning}
\begin{remark}{}{}
    Busy-wait semaphores are appropriate in a multiprocessor system when the waiting process has its own processor and is not wasting CPU time that could be used for computation.
    \begin{tip}
        They would be appropriate in a system with a little contention so that the waiting process would not waste too much CPU time
    \end{tip}
\end{remark}

\subsubsection{Producer-Consumer (P/C) Problem}\label{sub:cp_producer_consumer_p_c_problem} % (fold)
The producer-consumer problem is an example of an \textit{order-of-execution problem}.
There are two types of processes:
\begin{itemize}
    \item \textbf{producers}: a producer process executes a statement \textit{produce} to create a data element and then sends this element to the consumer process;
    \item \textbf{consumers}: upon receipt of a data element from a producer process, a consumer process executes a statement \textit{consume} with the data element as a parameter;
\end{itemize}
%
\paragraph{P/C with a Buffer}\label{par:pi_p_c_with_a_buffer} % (fold)
When a data element must be set from one process to another, the communication can be:
\begin{itemize}
    \item \textbf{synchronous}: communication cannot take place until both the producer and consumer are ready to do so;
    \item \textbf{asynchronous}: the communication channel itself has some capacity for storing data elements, uncoupling very useful for dynamic/open systems:
        \begin{itemize}
            \item temporal uncoupling among participants;
            \item dynamic set of processes;
        \end{itemize}
        \begin{note}
            Useful also when producers and consumers have different speed
        \end{note}
\end{itemize}
\begin{warning}
    The asynchronous case needs the introduction of a proper \textbf{buffer} where to store and retrieve data: shared data structures with a mutable state, read by consumers and written by producers
\end{warning}
% paragraph P/C with a Buffer (end)
%
\paragraph{P/C with Infinite Buffer}\label{par:pi_p_c_with_infinite_buffer} % (fold)
If there is an infinite buffer, there is only one interaction that must be synchronized, the consumer must not attempt a take operation from an empty buffer.
\begin{ctable}{|l|l|}
    \hline
    \multicolumn{2}{|l|}{\textbf{P/C with Infinite Buffer}} \\
    \hline
    \multicolumn{2}{|l|}{\texttt{UnboundedQueue<Item> buffer $\leftarrow$ empty queue}} \\

    \textbf{producer} & \textbf{consumer} \\
    \hline

\end{warning}

    In this example \texttt{append} and \texttt{take} are meant to be atomic: \texttt{nAvailItems} is called \textbf{resource semaphore}
\end{note}

\subsubsection{Dining Philosophers}\label{sub:pi_dining_philosophers} % (fold)
There is a secluded community of five philosophers who engage in only two activities: \textit{thinking} and \textit{eating}.
\\
Meals are taken communally at a table set with $5$ plates and $5$ forks, in the center of the table there is a bowl of spaghetti that is endlessly replenished.
\\
The spaghetti is hopelessly tangled and a philosopher needs \textit{two} forks in order to eat, each philosopher may pick up the forks on his left and on his right, but \textit{only one fork at a time}.
\begin{ctable}{|l|}
    \hline
    \textbf{Philosopher} \\
    \hline
    \texttt{loop forever} \\
    \textbf{p1:} \texttt{think}\\
    \textbf{p2:} \texttt{<pre-protocol>}\\
    \textbf{p3:} \texttt{eat}\\
    \textbf{p4:} \texttt{<post-protocol>}\\
    \hline
\end{ctable}
The problem is to design pre- and post-protocols to ensure the following properties:
\begin{itemize}
    \item a philosopher can eat only if he/she has two forks;
    \item \textbf{mutual exclusion}, no two philosophers may hold the same fork simultaneously;
    \item \textbf{freedom from deadlock};
    \item \textbf{freedom from starvation};
    \item efficient behaviour in the absence of contention;
\end{itemize}
%
\paragraph{First Attempt}\label{par:dp_first_attempt} % (fold)
Each fork is modelled as a semaphore:
\begin{itemize}
    \item wait $\Rightarrow$ taking a fork;
    \item signal $\Rightarrow$ putting down the fork;
\end{itemize}
\begin{ctable}{|l|}
    \hline
    \textbf{Dining Philosophers (first attempt)} \\
    \hline
    \texttt{semaphore array[0..4] fork $\leftarrow$ [1, 1, 1, 1, 1]} \\
    \hline
    \texttt{loop forever} \\
    \textbf{p1:} \texttt{think} \\
    \textbf{p2:} \texttt{wait(fork[i])} \\
    \textbf{p3:} \texttt{wait(fork[(i+1) \% N])} \\
    \textbf{p4:} \texttt{eat} \\
    \textbf{p5:} \texttt{signal(fork[i])} \\
    \textbf{p6:} \texttt{signal(fork[(i+1) \% N])} \\
    \hline
\end{ctable}
\begin{critical}[It can be proven taht no fork is ever held by two philosophers]
    Unfortunately this solution has \textbf{deadlocks}: under an \hyperref[def:interleaving]{Interleaving} that has all philosophers pick up their left
\end{critical}
To ensure liveness we can limit the number of philosophers eating simultaneously, or entering the dining room:
\begin{itemize}
    \item introducing meal, or room, tickets;
    \item $\dec N$ tickets for $N$ philosophers;
\end{itemize}
\begin{ctable}{|l|}
    \hline
    \textbf{Dining Philosophers (solution)} \\
    \hline
    \texttt{semaphore array[0..4] fork $\leftarrow$ [1, 1, 1, 1, 1]} \\
    \texttt{semaphore ticket $\leftarrow \pt{4,\pg{}}$} \\
    \hline

\subsubsection{Readers and Writers Problem}\label{sub:pi_readers_and_writers_problem} % (fold)
The problem of readers and writers is similar to the mutual exclusion problem in that several \hyperref[def:process]{Processes} are competing for access to a \hyperref[def:crit-sec]{Critical Section}.
In this problem we divide the \hyperref[def:process]{Processes} into two classes:
\begin{itemize}
    \item \textbf{readers}, which are required to exclude writers but not other readers;
    \item \textbf{writers}, which are required to exclude both readers and other writers;
\end{itemize}
The problem is an abstraction of \textit{access to databases}: no danger in having \hyperref[def:process]{Process} reading data concurrently, also writing or modifying data must be done under mutual exclusion to ensure consistency of the data.
\begin{critical}[Solutions must satisfy these \textit{invariants}]
    \[
        \begin{aligned}
            &nR \ge 0 \\
            &nW = 0 || nW = 1 \\
            &(nR > 0 \to nW = 0) \wedge (nW = 1 \to nR = 0)
        \end{aligned}
    \]
\end{critical}
Using a single \hyperref[def:semaphore]{Semaphore} functioning as a \hyperref[sub:cp_locks]{Lock}

    \hline

    \multicolumn{2}{|l|}{\texttt{DataBase dbase;}} \\

    \textbf{reader} & \textbf{writer} \\
    \hline
    \texttt{loop forever} & \texttt{loop forever} \\
    \textbf{p1:} \texttt{wait(rw)} & \textbf{q1:} \texttt{wait(rw)} \\

\subsubsection{The Cigarette Smoker's Problem}\label{sub:pi_the_cigarette_smoker_s_problem} % (fold)
Assume that there is a group of four people: $3$ smokers and $1$ agent.
To roll and smoke a cigarette three ingredients are needed: paper, tobacco and matches.
One of the smokers has an infinite supply of papers, another has an infinite supply of tobacco, and another has an infinite supply of all three ingredients.
\\
The four participants repeatedly perform the following operations: the agent puts two ingredients on the table; the smoker who has the remaining ingredient takes the two ingredients, rolls a cigarette, smokes it, and notifies the agent on completion.
Then the agent puts another two ingredients on the table, and so on.
\begin{note}
    The problem is to write a program to synchronize the agent and the smokers
\end{note}
%
\paragraph{Patil's Argument}\label{par:patil_s_argument} % (fold)
Patil's argument was that Dijkstra's \hyperref[def:semaphore]{Semaphore} primitives were limited: he used a cigarette smokers problem to illustrate this point by saying that it cannot be solved with \hyperref[def:semaphore]{Semaphores}.
However, Patil placed heavy constraints on his arguments: the \hyperref[def:process]{Process} code is the following (and not modifiable).
\begin{codeblock}{}
    shared: S array[1..3] binary semaphores, initially all 0
    agent: binary semaphore, initially 1

    local i,j: range over [1,2,3]
    loop
        set i and j (at random) from [1,2,3]
        wait(agent)
        signal(S[i])
        signal(S[j])
    end_loop
\end{codeblock}
\begin{note}
    The solution is not allowed to use conditional statements or an array of semaphores
\end{note}
\begin{warning}
    with these two constraints, a semaphore-based solution to the cigarette smokers problem is impossible
\end{warning}

\section{Monitors}\label{sec:pi_monitors} % (fold)
\begin{definition}{Monitor}{monitor}
    A \hyperref[def:conc-prog]{Concurrent Programming} data abstraction encapsulating the synchronization and mutual exclusion policy accessing it: state, operations and concurrency policy.
\end{definition}
Generalization of the \textit{kernel} or supervisor concept in operating systems, where critical sections such as the allocation of memory are centralized in a privileged program.
Application programs request services which are performed by the kernel, kernels are run in a HW mode that ensures that they cannot be interfered by application programs.
\begin{note}
    Monitors as decentralized versions of the monolithic kernel
\end{note}
Monitors are declared and created in different ways according to the specific language, an abstract representation:
\begin{codeblock}{}
    monitor MonitorName {
        declaration of permanent variables
        initialization statements
        procedures (or entries)
    }
\end{codeblock}
%
\subsection{Monitor Properties}\label{sub:pi_monitor_properties} % (fold)
Monitors as instances of abstract data type, only operations name are visible outside the monitor:
\begin{itemize}
    \item they are the interface;
    \item they provide the only gates through the ``wall'' defined by the monitor declaration;
    \item call to monitor procedures:
        \begin{codeblock}{}
    call MonitorName.OpName(params)
        \end{codeblock}
\end{itemize}
Statements within the monitor cannot access variables declared \textit{outside} the monitor, permanent variables are initialized before any procedures is called.
