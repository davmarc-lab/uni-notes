\chapter{Modelling Concurrent Systems}\label{chap:md_modelling_concurrent_systems} % (fold)
A \textbf{model} is a simplified representation of the real world and includes only those aspects of the real-world system relevant to the problem at hand.
\begin{example}{}{}
    An airplane model, used in wind tunnel tests, models only the external shape of the airplane
\end{example}
Models are widely used in engineering since they can be used to focus on a particular aspect of a real world system, such as the aerodynamic properties of an airplane or the strength of a bridge.
The reduction in scale and complexity achieved by modelling allows engineers to \textbf{analyse properties} such as the stress and strain on the structural components of a bridge.
\paragraph{Modelling}\label{par:md_modelling} % (fold)
The main roles of modelling are:
\begin{itemize}
    \item describing the behaviour of concurrent system in general;
    \item supporting the \textbf{design} of concurrent programs;
    \item \textbf{analysing} the behaviour of concurrent systems and of concurrent program execution;
\end{itemize}
A model represents the behaviour of concurrent programs at a level of abstraction that allows to focus on concurrency aspects.
\begin{quote}[Key usefulness]
    Models are based on proper formal/rigorous theories and frameworks that allow to \textit{mechanically} verify that they would satisfy correctness properties, required for the program when implemented.
\end{quote}
% paragraph Modelling (end)
%
\paragraph{Modelling Approaches}\label{par:md_modelling_approaches} % (fold)
Different kinds of approaches:
\begin{itemize}
    \item \textbf{\ac{lts}} and \textbf{Process Algebra}: modelling concurrency using interleaving;
    \item \textbf{Petri Nets}: approach not based on interleaving;
\end{itemize}

\section{Modelling Using LTS and FSP}\label{sec:md_modelling_using_lts_and_fsp} % (fold)
\acl{lts} are finite state machines with well-defined mathematical properties facilitating formal analysis and mechanical checking.
\\
Representing state machines graphically can limit the complexity of problems that can be addressed: to describe model we will use a \textbf{textual notation} called \ac{fsp}.
\begin{note}
    Technically \ac{fsp} is a process calculus
\end{note}

\subsection{Modelling a Process}\label{sub:md_modelling_a_process} % (fold)
\begin{definition}{Process}{process}
    In concurrent programming for \textbf{process} we mean the execution of a sequential program.
    The state of a process at any point in time consists of the values of explicit variables, declared by the programmer, and implicit variables such as the program counter and contents of data/address registers.
    \emptyln{}
    As a process executes, it transforms its state by executing statements, each statement consists of a sequence of one or more \textbf{atomic actions} that make \red{invisible} state changes.
\end{definition}
\paragraph{A More Abstract Model}\label{par:process_a_more_abstract_model} % (fold)
A more abstract model of a process --- ignoring the details of state representation and machine instructions --- is simply to consider a \textbf{process} as having a \textbf{state} modified by \textbf{indivisible} or \textbf{atomic action}.
Each action causes a \textit{transition} from the current state to the next state.
In order in which actions are allowed to occur is determined by a \textbf{transition graph} that is an abstract representation of a concurrent system in general, besides concurrent programming.

\subsubsection{Labelled Transition Systems}\label{sub:md_labelled_transition_systems} % (fold)
This form of state machine description is known as a \acl{lts}, since transitions are labeled with action names.
Formally a \textbf{transition system} is a pair $\pt{S,T}$ where:
\begin{itemize}
    \item $S$ is a set of states;
    \item $T$ is a subset of $S\times S$;
    \item we say there is a transition from state $p$ to state $q$ if $\pt{p,q} \in T$ and we denote it $p \to q$;
\end{itemize}
A \textbf{labelled transition system} is a tuple $\pt{S,\Lb, T}$ where:
\begin{itemize}
    \item $S$ is a set of states;
    \item $\Lb$ is a set of \textbf{labels};
    \item $T$ is a subset of $S\times \Lb\times S$ (labelled transition relation);
    \item we say there is a transition from state $p$ to state $q$ with label $\al$ if $\pt{q,\al,q} \in T$ and denote it $p \to^{\al}q$;
\end{itemize}
Labels can represent different things depending on the language of interest: expected input, events, conditions that must be true to trigger the transition, or actions performed during the transition.

\subsubsection{From Diagrams to an Algebra}\label{sub:md_from_diagrams_to_an_algebra} % (fold)
\ac{fsp} is a simple \textbf{algebraic notation} to describe process models: every \ac{fsp} has a corresponding state machine (\ac{lts}) description.
\emptyln{}
First description of \ac{fsp} main operators:
\begin{itemize}
    \item \textbf{action prefix}: $\pt{a \to P}$;
    \item \textbf{choice}: $\pt{a\to P | b \to Q}$;
    \item \textbf{parallel composition}: $\pt{P |\,| Q}$;
    \item \textbf{interaction}: through shared actions;
\end{itemize}
% subsubsection From Diagrams to an Algebra (end)

\paragraph{Action Prefix}\label{par:md_action_prefix} % (fold)
\begin{definition}{Action Prefix}{}
    If $x$ is an \textbf{action} and $P$ a \hyperref[def:process]{process} then the \textbf{action prefix} $\pt{x\to P}$ describes a process that initially engages in the action $x$ and then behaves exactly as described by $P$.
\end{definition}
The action prefix operator always has an action on its left and a process on its right.
\begin{note}
    In \ac{fsp} identifiers beginning with a \textbf{lowercase} letter denote actions and identifiers beginning with an \textbf{uppercase} letter denote processes
\end{note}
The definition of a new process: $Q = \pt{x\to P}$: a process can be defined in terms of other processes, by means of operators:
\begin{itemize}
    \item a process can be defined in terms of other processes, by means of operators;
    \item syntax/grammar: using a ``\texttt{.}'' as a terminator;
\end{itemize}
\begin{note}
    Non-finite processed specified by means of \textbf{recursive} specification: $P = \pt{x\to P}$;
\end{note}
Definition of multiple processes: $P = \pt{x\to Q},\, Q = \pt{y\to P}$;
\begin{example}{Light Switch}{switch-process}
    \begin{codeblock}{}
    SWITCH = OFF,
    OFF = (on->ON),
    ON = (off->OFF).
    \end{codeblock}
    Equivalent description (applying \textbf{substitution}):
    \begin{codeblock}{}
    SWITCH = (on->off->SWITCH).
    \end{codeblock}
    Corresponding \ac{lts}:
    \begin{center}
        \includegraphics[width=.4\textwidth]{assets/light-switch-ex.png}
    \end{center}
\end{example}
\begin{example}{Stop Process}{}
    The following example illustrates a process that engages in the action once and then stops:
    \begin{codeblock}
    ONESHOT = (once->STOP).
    \end{codeblock}
    \begin{note}
        \texttt{STOP} is a predefined with a specific behaviour
    \end{note}
    Corresponding \ac{lts}:
    \begin{center}

\subsection{Modelling Atomic Actions and Events}\label{sub:md_modelling_atomic_actions_and_events} % (fold)
\begin{definition}{Alphabet}{}
    The \textbf{alphabet} of a process is the set of actions in which it can engage: for example, the alphabet of the \hyperref[ex:switch-process]{\texttt{SWITCH}} is \texttt{\{on, off\}}.
\end{definition}
A message may \textbf{only engage in the actions in its alphabet}, however it may have actions in its alphabet in which it never engages.
In \ac{fsp} the alphabet of a process is determined implicitly by the set of actions referenced in its definition.
%
\paragraph{Modelling Choice}\label{par:alph_modelling_choice} % (fold)
Given a state, there could be possible multiple transitions, depending on events or internal state.
In \ac{fsp}:
\begin{description}
    \item[Choice construct] If $x$ and $y$ actions then $\pt{x\to P\,|\,y\to Q}$ describes a process which initially engages in either of the actions $x$ or $y$.
        After the first action has occurred, the subsequent behaviour is described by $P$ if the first action was $x$ and $Q$ if the first action was $y$.
\end{description}
\begin{example}{Drink Dispencer Machine}{}
    \ac{fsp} specification:
    \begin{codeblock}{}
    DRINKS = (red->coffee->DRINKS
             |blue->tea->DRINKS
             ).
    \end{codeblock}
    Corresponding \ac{lts}:
    \begin{center}

    \end{center}
\end{example}

\paragraph{Modelling Non-Deterministic Choice}\label{par:alph_modelling_non_deterministic_choice} % (fold)
The process $\pt{x\to P\, |\, x\to Q}$ is said to be \textbf{non-deterministic} since after the action $x$, it may behave as either $P$ or $Q$.
\begin{codeblock}{}
    COIN = (toss->heads->COIN
           |toss->tails->COIN

\end{codeblock}

\subsubsection{Indexed Processes and Actions}\label{sub:md_indexed_processes_and_actions} % (fold)
In \ac{fsp} both local processes and action label may be \textbf{indexed}, modelling processes and actions that can take \textit{multiple values}.
\begin{note}
    It greatly increases the expressive power of the notation
\end{note}
\begin{codeblock}{Buffer containing a single value}
    BUFF = (in[i:0..3]->out[i]->BUFF).
\end{codeblock}
It inputs a value in the range $0$ to $3$ and then outputs that value.
This is equivalent to:
\begin{codeblock}{}
    BUFF = (in[0]->out[0]->BUFF
        |in[1]->out[1]->BUFF
        |in[2]->out[2]->BUFF
        |in[3]->out[3]->BUFF
        ).
\end{codeblock}
\begin{warning}
    Indices always have a finite range of values that they can take: this ensures that the models we describe in \ac{fsp} are finite and thus potentially mechanically analysable
\end{warning}
Corresponding \ac{lts}:
\begin{cimage}
    \includegraphics[width=.4\textwidth]{assets/buf-lts-visual.png}
\end{cimage}

\paragraph{Specifying a Range}\label{par:md_specifying_a_range} % (fold)
\begin{codeblock}{}
    range T = 0..3

\paragraph{Process Parameters}\label{sub:md_process_parameters} % (fold)
Processes may be parameterised so that they may be described in a general form and modelled for a particular parameter value.
\emptyln{}
For instance, the single-slot buffer described before can be described as a parameterised process for values in the range $0$ to $N$ as follows:
\begin{codeblock}{}
    BUFF(N=3) = (in[i:0..N]->out[i]->BUFF).
\end{codeblock}
using constants:
\begin{codeblock}{}
    const N = 3
    BUFF = (in[i:0..N]->out[i]->BUFF).
\end{codeblock}
\begin{note}[FPS syntax details]
    \begin{itemize}
        \item parameters must be given a default value and must start with an uppercase letter;
        \item the scope of the parameter is the process definition;
        \item $N$ may be given a fixed constant value;
    \end{itemize}
\end{note}

\subsubsection{Guarded Actions}\label{sub:md_guarded_actions} % (fold)
It is often useful to define particular actions as \textbf{conditional}, depending on the current state of the machine.
We use \textbf{Boolean} guards to indicate that a particular action can only be selected if its guard is selected.
\emptyln{}
The choice \texttt{(when B x->P | y->Q)} means that when the guard \texttt{B}  is true then the actions \texttt{x} and \texttt{y} are both eligible to be chosen, otherwise if \texttt{B} is false then the action \texttt{x} cannot be chosen.
\begin{example}{}{}
    A \texttt{COUNT} process that encapsulated a count variable, that can be increased by \texttt{inc} operations and decreased by \texttt{dec} operations.
    The count is not allowed to exceed \texttt{N} or be less than zero.
    \begin{codeblock}{}
    COUNT (N=3) = COUNT[0],
    COUNT[i:0..N] = (when(i<N) inc->COUNT[i+1]
        |when(i>0) dec->COUNT[i-1]
    ).
    \end{codeblock}
    Corresponding \ac{lts}:
    \begin{center}
        \includegraphics[width=.4\textwidth]{assets/guard-actions-visaul.png}
    \end{center}
\end{example}

\subsection{Modelling Concurrency}\label{sub:md_modelling_concurrency} % (fold)
In \ac{fsp} a concurrent system can be modelled then as a composition of processes, using parallel operator:
\begin{itemize}
    \item if \texttt{P} and \texttt{Q} are processes then \texttt{(P || Q)} represents the \textbf{concurrent execution} of \texttt{P} and \texttt{Q};
    \item the operator \texttt{||} is the \red{parallel composition operator};
\end{itemize}
Parallel composition is a process itself, which is represented as a \textbf{state machine} in the same way as any other process: the state machine representing the \textbf{composition generates all possible interleavings} of the traces of its constituent processes.
\begin{note}[Primitive Processes]
    \textbf{Primitive Processes} are defined using action prefix and choice while \textbf{composite} processes are defined using only parallel composition.
    \begin{critical}
        Maintaining this strict distinction between primitive and composite precesses is required to ensure that the models described by \ac{fsp} are \textbf{finite}
    \end{critical}
\end{note}
\begin{example}{A process of two parallel processes}{}
    The process:
    \begin{codeblock}{}
    ITCH = (scratch->STOP).
    \end{codeblock}
    has a singe trace consisting of the action: \texttt{scratch}
    \emptyln{}
    The process:
    \begin{codeblock}{}
    CONVERSE = (think->talk->STOP).
    \end{codeblock}
    has the single trace: \texttt{think->talk}
    \emptyln{}
    The composite process:
    \begin{codeblock}{}
    ||CONVERSE_ITCH = (ITCH || CONVERSE).
    \end{codeblock}
    has the following traces:
    \begin{codeblock}{}
    think->talk->scratch
    think->scratch->talk
    scratch->think->talk
    \end{codeblock}
    \begin{center}
        \includegraphics[width=.6\textwidth]{assets/parallel-process-ex.png}
    \end{center}
    \begin{note}
        The state machine represented is formed by the \textbf{product Cartesian} of its constituents
    \end{note}
\end{example}
\begin{example}{Another Parallel Example}{}
    The following processes model a clock radio which incorporates two independent activities: a clock which ticks and a radio which can be switched on and off.
    \begin{codeblock}{}
    CLOCK = (tick->CLOCK).
    RADIO = (on->off->RADIO).
    ||CLOCK_RADIO = (CLOCK || RADIO).
    \end{codeblock}
    \begin{cimage}
        \includegraphics[width=.6\textwidth]{assets/clock-radio-parallel-ex.png}
    \end{cimage}
    Possible traces:
    \begin{codeblock}{}
    on->tick->tick->off->tick->tick->tick->on->off->...
    tick->on->off->on->off->on->off->tick->on->tick->...
    \end{codeblock}
\end{example}
\subsubsection{Parallel Algebra}\label{sub:md_parallel_algebra} % (fold)
The parallel composition operator obeys some simple algebric laws:
\begin{itemize}
    \item \textbf{commutative}: \texttt{(P || Q) = (Q || P)}
    \item \textbf{associative}: \texttt{P || (Q || R)) = ((P || Q) || R) = (P || Q || R)}
\end{itemize}
\begin{note}
    Taken together these mean that the brackets can be dispensed with and the order that processes appear in the composition is \textbf{irrelevant}
\end{note}

\subsubsection{Concurrency by Interleaving}\label{sub:md_concurrency_by_interleaving} % (fold)
The execution of a concurrent program consists of multiple processes active at the same time.
\\
Since we want to design concurrent programs which works \textbf{independently} of the number of processors and the scheduling strategy, we \textbf{choose not to model relative speed} but simply that processes \textbf{execute at arbitrary relative speeds}.
\begin{note}
    It means that a process can take an \textit{arbitrary long time} to proceed from one action to the next
\end{note}
\begin{warning}[Abstracting away from execution time]
    \begin{itemize}
        \item the disadvantage that we can say nothing about the real-time properties of programs but has the advantage that we can \textbf{verify} other properties \textbf{independently} of the particular configuration of the computer and its operating system;
        \item this independence is clearly important for the portability of concurrent programs;
    \end{itemize}
\end{warning}
A classic approach to model concurrency, abstracting from time, is using \textbf{interleaving}.
\\
\begin{definition}{Interleaving}{}
    The execution of concurrent processes each represented by a sequence of actions is modelled by a single sequence of actions (a \textbf{scenario} or \textbf{trace}) obtained by interleaving the actions of each process.
    The situation in which two actions \texttt{a} and \texttt{b} of two different processes are executed simultaneously is modelled in the scenario as a sequence either in the order \texttt{a->b} or \texttt{b->a}.
\end{definition}
\begin{critical}[Non Determinism]
    Due to \textbf{interleaving}, we can have different possible scenarios resulting from the execution of concurrent processes: the number of possible scenarios could be even not finite
\end{critical}
% subsubsection Concurrency by Interleaving (end)
%
\subsubsection{Arbitrary Interleaving}\label{sub:md_arbitrary_interleaving} % (fold)
\begin{definition}{Arbitrary Interleaving}{}
    \textbf{Arbitrary Interleaving} is a good model of concurrent execution since it abstracts the way processors switch between processes as a result of external interrupts.
    \emptyln{}
    The timing of interrupts relative to process execution cannot be predetermined since actions in the real world cannot be predicted exactly.
\end{definition}

\subsection{Modelling Interactions}\label{sub:md_modelling_interactions} % (fold)
\begin{definition}{Interactions}{}
    \textbf{Interactions} among processes is modelled through \textbf{shared actions}, that is processes having alphabets with actions in common.
\end{definition}
\begin{note}[Interaction Rule]
    While unshared actions may be arbitrary interleaved, a shared action must be executed at the same time by all the processes that participate in that shared action
\end{note}
\begin{example}{\texttt{meet} action in \texttt{BILL} and \texttt{BEN} processes}{}
    \begin{codeblock}{}
    BILL = (play->meet->STOP).
    BEN = (work->meet->STOP).
    ||BILL_BEN = (BILL || BEN).
    \end{codeblock}
    In the example, \texttt{BILL} and \texttt{BEN} processes share the action \texttt{meet}, the possible execution traces of the composition are:
    \begin{codeblock}{}
    play->work->meet
    work->play->meet
    \end{codeblock}
    The state machine for the composite process is:
    \begin{cimage}
        \includegraphics[width=.6\textwidth]{assets/bill-ben-meet-ex.png}
    \end{cimage}
\end{example}
\begin{example}{User and Make}{user-maker}
    This example consists of a process that manufactures an item and then signals that the item is ready for use by a shared action.
    \begin{codeblock}{}
    MAKER = (make->ready->MAKER).
    USER = (ready->use->USER).
    ||MAKER_USER = (MAKER || USER).
    \end{codeblock}
    Corresponding \ac{lts}:
    \begin{cimage}
        \includegraphics[width=.6\textwidth]{assets/user-maker-ex.png}
    \end{cimage}
    Possible execution traces:
    \begin{codeblock}{}
    make->ready->use->make->ready->...
    make->ready->make->use->ready->...
    \end{codeblock}
    \begin{warning}
        After the initial item is manufactured and becomes ready, manufacture and use can proceed in parallel since the actions make and use can occur in any order.
        \emptyln{}
        However, it is always the case that an item is made \textit{before} it is used since the first action is make in all traces.
        The second trace shows that two items can be made before the first is used.
    \end{warning}
\end{example}

\subsubsection{Handshake}\label{sub:md_handshake} % (fold)
Suppose that this is undesirable behaviour, and we don't wish the \hyperref[ex:user-maker]{\texttt{MAKER}} process to get ahead in this way.
The solution is to modify the model so that the user indicates that the item is used: \texttt{used} action/event.
\begin{codeblock}{}
    MAKER2 = (make->ready->used->MAKER2).
    USER2 = (ready->use->used->USER2).
    || MAKER_USER2 = (MAKER2 || USER2).
\end{codeblock}
\begin{note}[Handshake]
    The \texttt{used} action is called \textbf{handshake}, as an action which is acknowledged by another.
    This \texttt{used} action is shared with the \texttt{MAKER} who now cannot proceed to manufacture another item until the first is used 
\end{note}

    \includegraphics[width=.6\textwidth]{assets/user-maker-handshake-ex.png}
\end{cimage}

\subsubsection{Multi Party Synchronisation}\label{sub:md_multi_party_synchhronisation} % (fold)
Many processes can engage in a shared action:
\begin{codeblock}{}
    MAKE_A = (makeA->ready->used->MAKE_A).
    MAKE_B = (makeB->ready->used->MAKE_B).
    ASSEMBLE = (ready->assemble->used->ASSEMBLE).
    ||FACTORY = (MAKE_A || MAKE_B || ASSEMBLE).
\end{codeblock}
\begin{itemize}
    \item \texttt{assemble} cannot take place until both parts are ready:
    \item \texttt{maker}s are not permitted to get ahead of users;
\end{itemize}

\subsection{Parallel Composition of Composite Processes}\label{sub:md_parallel_composition_of_composite_processes} % (fold)
Since a parallel composition of processes is itself a process, called a \textbf{composite process}, it can be used in the definition of further compositions.
\begin{codeblock}{}
    MAKE_A = (makeA->ready->used->MAKE_A).
    MAKE_B = (makeB->ready->used->MAKE_B).
    ||MAKERS = (MAKE_A || MAKE_B).
\end{codeblock}
The rest of the factory description now becomes:
\begin{codeblock}{}
    ASSEMBLE = (ready->assemble->used->ASSEMBLE).
    ||FACTORY = (MAKERS || ASSEMBLE).
\end{codeblock}
\begin{warning}
    Substituting the definition for \texttt{MAKERS} in \texttt{FACTORY} and applying the commutative and associative laws for parallel composition stated in the last section results in the original definition for \texttt{FACTORY} in terms of primitive processes
\end{warning}

\subsection{Parallel Composition of Multiple Instances}\label{sub:md_parallel_composition_of_multiple_instances} % (fold)
Given the definition of a \hyperref[def:process]{process}, we often want to use more than one copy of that process in a program or system model.
For example, given the definition for a switch:
\begin{codeblock}{}
    SWITCH = (on->off->SWITCH).
\end{codeblock}
We may wish to describe from a system that is the composition of two distinct switches.
However, if we describe this system as:
\begin{codeblock}{}
    (SWITCH || SWITCH)
\end{codeblock}
the composition is indistinguishable from a single switch since the two switches processes synchronize on their shared actions \texttt{on} and \texttt{off}.
\subsubsection{Process Labelling}\label{sub:md_process_labelling} % (fold)
We must ensure that the \textbf{actions} of each \texttt{SWITCH} process are not shared: this is done by means of \textbf{process labelling}.
\begin{codeblock}{}
    ||TWO_SWITCH = (a:SWITCH || b:SWITCH).
\end{codeblock}
The state machine representation:

\subsection{Parametrised Composite Processes}\label{sub:md_parametrised_composite_processes} % (fold)
Composite processes can be parameterised using the \textbf{\texttt{forall}} construct:
\begin{codeblock}{}
    forall [i:1..N] P(i)
\end{codeblock}
is the parallel composition:
\begin{codeblock}{}
    (P(1) || ... || P(N))
\end{codeblock}
\begin{example}{Array of \texttt{SWITCHES}}{}
    \begin{codeblock}{}
    ||SWITCHES(N=3) = (forall[i:1..N] s[i]:SWITCH).
    \end{codeblock}
\end{example}
An equivalent but shorter definition is:
\begin{codeblock}{}
    ||SWITCHES(N=3) = (s[i:1..N]:SWITCH).
\end{codeblock}

\subsection{Using Set of Prefix Labels}\label{sub:md_using_set_of_prefix_labels} % (fold)
Labelling can be done using set of prefix labels using \texttt{\{a1,.., ax\}::P}:
\begin{itemize}
    \item replaces every action label $n$ in the alphabet of $P$ with the labels: \texttt{a1.n, ..., ax.n}
    \item every transition \texttt{(n->Q)} in the definition of $P$ is replaced with the transitions: \texttt{(\{a1.n, ... , ax.n\}->Q}
\end{itemize}
This is useful when we have processes that can interact with other multiple processes:
\begin{codeblock}{}
    RESOURCE = (acquire->release->RESOURCE).
    USER = (acquire->use->release->USER).
    ||RESOURCE_SHARE = (a:USER || b:USER || {a,b}::RESOURCE)
\end{codeblock}
\begin{cimage}
    \includegraphics[width=.6\textwidth]{assets/user-res-ex.png}
\end{cimage}

\subsubsection{Binding Interactions Through Relabelling}\label{sub:md_binding_interactions_through_relabelling} % (fold)
Individual processes can be designed with their own proper alphabet.
When creating composite processes composing independent processes we may need to create a correspondence among the actions that should synchronise by means of \textbf{relabelling}.
\emptyln{}
\textbf{Relabelling functions} are applied to change the names of actions labels, the general form is:
\begin{codeblock}{}
    /\{newlabel_1/oldlabel_1,...newlabel_n/oldlabel_n\}
\end{codeblock}
\begin{example}{Client Server Example}{}
    A server process that provides some service and a client process that invokes the service are described below:
    \begin{codeblock}{}
    CLIENT = (call->wait->continue->CLIENT).
    SERVER = (request->service->reply->SERVER).
    ||CLIENT_SERVER = (CLIENT || SERVER)/{call/request, reply/wait}.
    \end{codeblock}
\end{example}

\subsection{Hiding and Silent Actions}\label{sub:md_hiding_and_silent_actions} % (fold)
Sometimes is useful to make process actions ``private'', that is not to be used for interacting with other processes.
\emptyln{}
When applied to a process $P$, the \textbf{hiding operator} removes the action names from the alphabet of $P$ and makes these concealed actions \textbf{silent}.
In \ac{fsp}, and process calculi, this can be done by using: \texttt{\textbackslash\{a1..ax\}}
\begin{note}
    Silent actions are uniformly represented by the symbol $\tau$ (\textbf{tau})
\end{note}
In different processes silent actions are not shared, the hidden actions become unobservable in that they cannot be shared with another process and so cannot affect the execution of another process.
\emptyln{}
The dual operator \texttt{@\{a1..ax\}} ``expose'' actions: when applied to a process $P$, the interface operator \texttt{@\{a1..an\}} hides all actions in the alphabet of $P$ not labeled in the set \texttt{\{a1..\}}
\begin{example}{}{}
    In \texttt{USER} process definition, hiding the use action in two different approaches:
    \begin{codeblock}{}
    USER = (acquire->use->release->USER)\{use}.
    USER = (acquire->use->release->USER)@{acquire,release}.
    \end{codeblock}
    \begin{cimage}
        \includegraphics[width=.6\textwidth]{assets/user-hiding-ex.png}
    \end{cimage}
\end{example}

\subsection{Sequential Processes}\label{sub:sequential_processes} % (fold)
Although abstractly a process always means the same thing, for pragmatic implementation reason \ac{fsp} divides processes into three types:
\begin{itemize}
    \item \textbf{local processes} that define a state within a primitive process;
    \item \textbf{primitive processes} defined by a set of local processes;
    \item \textbf{composite processes} that use parallel composition, relabelling and hiding to compose primitive processes;
\end{itemize}
A local process is defined using \texttt{STOP}, \texttt{ERROR}, action prefix and choice.
We now extend our definition of \hyperref[def:process]{processes} to include \textbf{sequential processes}.
\begin{definition}{Sequential Process}{seq-process}
    A \textbf{sequential process} is a process that can \textbf{terminate}: a process can terminate if the local process \textbf{END} is reachable from its start state
\end{definition}
%
\subsubsection{End Local Process}\label{sub:md_end_local_process} % (fold)
The local process \texttt{END} denotes the state in which a process successfully terminates.
A \hyperref[def:process]{process} engages in no further actions after \texttt{END}; same semantics as \texttt{STOP}, however \texttt{STOP} denotes a state in which a process has halted prematurely (usually due to communication deadlock).
\begin{cimage}
    \includegraphics[width=.6\textwidth]{assets/bomb-end-ex.png}
\end{cimage}
% subsubsection End Local Process (end)

\subsubsection{Sequential Composition}\label{sub:md_sequential_composition} % (fold)
The definition of \hyperref[def:seq-process]{sequential process} is useful for introducing a further kind of composition, useful for modularity: \textbf{sequential composition}.
\emptyln{}
If $P$ is a sequential process and $Q$ is a local process, then \texttt{P;Q} represents the sequential composition such that when $P$ terminates, \texttt{P;Q} becomes the process $Q$.
If we define a process \texttt{SKIP = END} then \texttt{P;SKIP $\equiv$ P} and \texttt{SKIP;P $\equiv$ P}.
\begin{codeblock}{}
    SP(I=0) = (a[I]->END).
    P123 = (start->SP(1);SP(2);SP(3);END).
    LOOP = P123;LOOP.
\end{codeblock}
\begin{cimage}
    \includegraphics[width=.6\textwidth]{assets/seq-comp-loop-visual.png}
\end{cimage}
A sequential composition in \ac{fsp} always take the form: \texttt{SP1;SP2;..SPn;LP} where \texttt{SP1,..,SPn} are seuqential processes and \texttt{LP} is a local process.
\begin{note}
    A sequential composition can appear anywhere in the definition of a primitive process that a local process reference can appear
\end{note}
%
\paragraph{Recursive Context}\label{par:sc_recursive_context} % (fold)
Sequential composition can be used in a recursive context.
\begin{codeblock}{}
    const N = 3
    R(I=0) = if (I<N) then
            (a[I]->R(I+1);END)
        else
            END.
\end{codeblock}
\begin{cimage}
    \includegraphics[width=.6\textwidth]{assets/recursive-seq-comp-ex.png}
\end{cimage}
Process \texttt{R} is defined as the sequential composition of sequential processes \texttt{R(I)} for values of $I$ from $0$ to $2$ and the local process \texttt{END} when $I=3$.
\begin{note}[If Construct]
    The \texttt{P = if <cond> then Q else R} means that the process \texttt{P} is defined as \texttt{Q} if the boolean condition is \texttt{true}, otherwise it is defined as \texttt{R}
\end{note}

\subsection{Parallel Composition and Sequential Processes}\label{sub:md_parallel_composition_and_sequential_processes} % (fold)
The parallel composition \texttt{SP1 || SP2} of two sequential processes \texttt{SP1} and \texttt{SP2} terminates when both of these processes terminate: if termination is reachable in \texttt{SP1 || SP2} then it is a sequential process.

\section{Modelling Using Petri Nets}\label{sec:md_modelling_using_petri_nets} % (fold)
A \textbf{\ac{pn}} is an abstract formal model of information flow.
It describes and analyse the flow of information and control in systems, in particularly represent systems that may exhibit asynchronously and concurrent activities.
\begin{note}[Major Use]
    Modelling of systems of events in which it is possible for some events to occur concurrently, but there are constraints on the concurrence, precedence, or frequency of these occurrences
\end{note}
\subsection{Petri Net Graph}\label{sub:md_petri_net_graph} % (fold)
Bi-partite graphs representing a \ac{pn} with two types of \textit{nodes}:
\begin{itemize}
    \item \textbf{places} represented with a circle;
    \item \textbf{transitions} represented with a bar;
\end{itemize}
Each node can be connected by directed arcs, for example from node $i$ to node $j$ : $i$ is an \textbf{input} to $j$ and $i$ is an \textbf{output} of $i$.
\begin{note}
    It models the \textbf{static} properties of the system
\end{note}
% subsection Petri Net Graph (end)
%
\subsection{Token and Markings}\label{sub:md_token_and_markings} % (fold)
In addition to the static properties represented by the graph, a \ac{pn} has \textbf{dynamic properties} that result from its \textbf{execution}: the execution is controlled by the position and movement of markers called \textbf{tokens} in the net.
\begin{cimage}
    \includegraphics[width=.4\textwidth]{assets/20260921_133335.png}
    \caption{Tokens are indicated by black dots}\label{fig:20260921_133335}
\end{cimage}
\begin{note}
    A \ac{pn} with tokens is called \textbf{marked Petri Net}
\end{note}

\subsubsection{Execution Rules}\label{sub:md_execution_rules} % (fold)
Tokens are moved by the \textit{firing} of transitions of the net.
A \textbf{transition} must be enabled in order to fire: enabled when all of its input places have a tiken in them.
The transition fires by removing the enabling tokens from their input places and generating new tokens which are deposited in the output place of the transition.

\subsubsection{Weighted Arcs}\label{sub:md_weighted_arcs} % (fold)
A variant consider also weights for arcs: a \textbf{transition $t$ is enabled} if each input place $p$ of $t$ is marked with at least $w\pt{p,t}$ tokens, where $w\pt{p,t}$ is the weight of the arc from $p$ to $t$.
\emptyln{}
A firing of an \textbf{enabled transition $t$ removes} $w\pt{p,t}$ tokens from each input place $p$ of $t$, and adds $w_1$ tokens to each output place $p$ of $t$, where $w\pt{p,t}$ is the weight of the arc from $t$ to $p$.

\subsection{Modelling with Petri Nets}\label{sub:md_modelling_with_petri_net} % (fold)
\ac{pn} can be used to model quite naturally concurrent systems in terms of:
\begin{itemize}
    \item \textbf{events} and \textbf{conditions};
    \item relationship among them;
\end{itemize}
\begin{description}
    \item[Interpretation] In a system at any given time certain conditions will hold.
        The fact that these conditions hold may cause the occurrence of certain events; this occurrence may change the state of the system causing:
        \begin{itemize}
            \item some of the previous conditions to cease holding;
            \item other conditions to begin to hold;
        \end{itemize}
        \begin{note}
            Firing a transition means the occurrence of an event considered instantaneous or better: \textbf{atomic change} of the system
        \end{note}

            \hline
            Input signals & Signal processor & Output signal \\
            \hline
            Resource needed & Task or Job & Resource Released \\
            \hline
            Conditions & Clause in Logic & Conclusion \\
            \hline
            Buffers & Processor & Buffer \\
            \hline
        \end{ctable}

\end{description}
