\section{Thread Safety}\label{sec:ts_thread_safety} % (fold)
\begin{definition}{Thread Safe}{tsafe}
    A class is \textbf{thread safe} if continues to behave correctly when accessed from multiple threads, regardless of the scheduling or interleaving of the execution of those threads by the runtime environment.
    \begin{note}
        Without additional synchronization or other coordination on the part of the calling code
    \end{note}
\end{definition}
Correctness means that a class conforms to its specification, a good specification defines:
\begin{itemize}
    \item \textbf{invariants} constraining an object's state;
    \item \textbf{post-conditions} describing the effects if its operations;
\end{itemize}
\begin{note}
    Thread-safe classes encapsulate any needed synchronization, so the clients don't need to provide their own
\end{note}
%
\subsection{Shared Mutable State}\label{sub:ts_shared_mutable_state} % (fold)
Writing thread-safe code is -- at its core -- about \textit{managing access to state} and in particular to \textbf{shared} and \textbf{mutable state}:
\begin{definition}{Shared}{shared}
    A variable or object could be accessed by multiple threads.
\end{definition}
\begin{definition}{Mutable}{mutable}
    Its value could change during its lifetime.
\end{definition}
\begin{critical}[Race Conditions]
    If multiple threads access the same \hyperref[def:mutable]{Mutable} state variable without appropriate synchronization, the program is broken
\end{critical}
There are three ways to fix it:
\begin{itemize}
    \item don't save state variable across threads;
    \item make the state variable across threads;
    \item use synchronization whenever accessing the state variable;
\end{itemize}

\subsubsection{Stateless \& Stateful Object}\label{sub:stateless_stateful_object} % (fold)
\textbf{Stateless} objects are always \hyperref[def:tsafe]{Thread Safe}: actions of a thread accessing a stateless object cannot affect the correctness of operations in other threads.
\begin{note}
    Thread safety is undermined as soon as we share and access in R/W \textbf{stateful} objects: \hyperref[def:mutable]{Mutable} state-full objects in particular
\end{note}
% subsubsection Stateless \& Stateful Object (end)

\subsection{Race Conditions}\label{sub:race_conditions} % (fold)
The concurrent execution of non-atomic sequence of statements that should be considered atomic, generate \textbf{race condition}.
\begin{note}
    It occurs when the \textbf{correctness of a computation} depends on the relative timing or interleaving of multiple threads by the runtime
\end{note}
%
\subsubsection{Lost Updates \& Check-and-Act}\label{sub:lost_updates_check_and_act} % (fold)
\begin{definition}{Lost Updates}{lost-update}
    When executing concurrently non-atomic read-modify-write operations (\texttt{count++}).
\end{definition}
\begin{definition}{Check-and-Act}{check-act}
    When a potentially state observation is used to make a decision on what to do next.
    \begin{note}
        Since check and act are not atomic, the state can change after check and before act
    \end{note}
    \begin{example}{}{}
        \begin{codeblock}[txt]{}
        if (file X doesn't exists)  -- check
            then create file X      -- act
        \end{codeblock}
    \end{example}
\end{definition}
\begin{note}[Compound Atomic Actions]
    \hyperref[def:check-act]{Check-and-Act} and read-modify-write are examples of compound actions: the sequence of operation that must be executed atomically in order to remain \hyperref[def:tsafe]{Thread Safe}
\end{note}

\subsubsection{Atomic Compound Actions in Java}\label{sub:atomic_compound_actions_in_java} % (fold)
Compound actions and atomic statements blocks in Java can be realized by means of synchronized blocks or methods.
\begin{codeblock}[java]{}
    synchronized(lock) {
        statement
        statement
        statement
    }
\end{codeblock}
A synchronized block has two parts:
\begin{itemize}
    \item a reference to an object that will serve as the \textbf{lock};
    \item block of code to be guarded by the \textbf{lock};
\end{itemize}
\begin{note}
    Mostly used at a \textit{method} level: synchronized attributes.
\end{note}
\paragraph{Intrinsic Lock and Entry Set}\label{par:intrinsic_lock_and_entry_set} % (fold)
Atomic blocks work by exploiting the \textbf{lock} embedded in each Java object called \textbf{intrinsic lock} or monitor lock.
\begin{note}[Functioning as a guard for the block]
\end{note}
The lock is automatically acquired and then released by a thread respectively when entering and exiting the block, if the lock is already acquired the thread is blocked (suspended) and added to the entry set.
When a thread exited the block, one thread of the entry set is selected and re-activated.
\begin{warning}
    If the lock is not released by the thread inside the block, threads in the entry set are blocked forever (\textbf{starvation})
\end{warning}
\begin{note}[For static methods and fields, the lock is associated to the related \texttt{Class} object]
    For \textbf{synchronized methods} the object serving as lock is \texttt{this}
\end{note}

\subsection{Lock Reentrancy}\label{sub:lock_reentrancy} % (fold)
\begin{definition}{Look Reentrancy}{}
    When \textbf{locks} are acquired on a \textit{per-thread} basis, \textit{per-invocation} basis is adopted as default locking behaviour for Pthreads mutex-es instead.
\end{definition}
\begin{note}
    Java intrinsic locks are \textbf{reentrant}: if a thread tries to acquire a lock that it already holds,  the request succeeds
\end{note}
Reentrancy facilitates encapsulation of locking behaviour and thus simplify the development of Object-Oriented concurrent code.
\begin{codeblock}[java]{}
    public class Widget {
        public synchronized doSomething() {...}
    }

    public class LoggingWidget extends Widget {
        public synchronized void doSomething() {
            System.out.println(toString() + ": calling doSomething");
            super.doSomething();
        }
    }
\end{codeblock}
\begin{critical}[Without reentrancy the code above would lead to a deadlock]
\end{critical}
%
\subsubsection{Performance: Poor Concurrency Problem}\label{sub:performance_poor_concurrency_problem} % (fold)
The misuse of atomic blocks can lead to performance problems: sequentializations $\Rightarrow$ strong impact on \textbf{speed-up} (poor performance).
\emptyln{}
From a performance perspective, it is important to do a careful choice of what parts must be designed and implemented as critical sections.
\begin{tip}[Practial Rule]
    Minimize the time in which a lock is retained, \textbf{but} don't trade performance with safety
\end{tip}
